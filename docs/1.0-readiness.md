# Khrona 1.0 readiness notes

Status: planned acceptance criteria. This checklist tracks the remaining 1.0 work after PR #11's correctness fixes. Completion requires implementation, documentation, and recorded validation on the release commit.

## Existing Dockerized Ktor E2E baseline

The existing [Ktor generator suite](../khrona-ktor/src/test/kotlin/io/khrona/ktor/e2e/KtorGeneratorDockerE2ETest.kt) tests Khrona as a dependency of a newly generated application:

1. The [e2eTest Gradle task](../khrona-ktor/build.gradle.kts) publishes core, Ktor, Memory, JDBC, and Redis artifacts to `mavenLocal()` and passes the current project version to the tests.
2. Each scenario runs a JDK 21 Docker container with the official Ktor CLI and scaffolds a fresh project with `ktor new`.
3. The generated project resolves Khrona from the local Maven repository mounted into the container, adds its backend dependencies, configures the Ktor plugin, and starts a real HTTP server.
4. The test exercises the application through HTTP and checks backend-specific outcomes.

| Scenario | Existing coverage |
| --- | --- |
| Memory | One-time, interval and manual execution; cron registration; structured payload and MDC correlation ID propagation; retry/timeout paths; direct store fencing checks. |
| PostgreSQL / JdbcJobStore | Store-backed execution, interval scheduling, FORBID/REPLACE, ignored misfires, retention cleanup, and ownership fencing. |
| Redis / RedisJobStore | Interval execution, REPLACE, heartbeat extension, stale recovery, retention cleanup, and ownership fencing. |

Run explicitly with Docker available:

```bash
./gradlew :khrona-ktor:e2eTest
```

The suite is tagged `e2e`, excluded from ordinary `test` runs, and runs in the dedicated `e2e` job in [CI](../.github/workflows/ci.yml). It needs network access for the container image, Ktor generator/templates, and uncached build dependencies. Test reports are written to `khrona-ktor/build/reports/tests/e2eTest/`.

This baseline verifies generated-app integration with locally published artifacts. Add a separate consumer smoke check for the actual release repository/artifacts. The fixture's `/health` route returns application-level HTTP readiness; it does not implement the scheduler/store health indicator planned below. The current cron assertion checks registration, rather than waiting for a cron occurrence. Existing scenarios do not establish populated-version upgrades, arbitrary Redis Cluster support, network partitions, or failover behavior.

## Remaining acceptance areas

| Area | What remains | Evidence required before closing |
| --- | --- | --- |
| Stable API and SPI | Finalize handler/store contracts; provide execution context with execution ID, attempt, and scheduled time; add compatibility checks and a deprecation policy. | API compatibility fixtures, shared store contract tests, and a generated Ktor consumer using the supported handler API. |
| Observability | Metrics for lag, duration, failures, recovery and DLQ; scheduler health/readiness; useful failure diagnostics. | Tests of successful/failing jobs, store outages and recovery; generated apps expose observable results through host-owned adapters. |
| Operator controls | Query executions, pause/resume, request cancellation, inspect/replay dead letters, and reconcile removed jobs. Immediate triggering already exists. | Bounded store queries, explicit operation semantics, multi-node contract tests, and generated-app workflows. |
| Safe upgrades | Versioned migrations, populated-database upgrade tests, and clear rollback/recovery instructions. | Previous-version data fixtures upgraded and reopened by the candidate release, with execution/state invariants checked. |
| Distributed failure evidence | Verified clock-skew policy, process-crash recovery, partitions, failover, and sustained-load behavior. Document blocking-handler and cooperative-cancellation limits. | Controlled fault-injection and multi-node tests, plus soak/performance results and an explicit delivery contract. |
| Release and support discipline | Test-gated publishing, dependency scanning, security reporting, supported deployment matrix, and an operations runbook. | Release workflow checks, a consumer artifact smoke test, documented support/security procedures, and a completed release checklist. |

### API-1: Stable API and SPI

- [ ] Define the supported public Kotlin API and any offered Java entry points; stabilize `JobStore` contracts and failure/ownership semantics.
- [x] Expose execution context containing execution ID, attempt, and scheduled time. Document identifier stability across retries and lease reclaims so handlers can implement idempotency.
- [ ] Document payload serialization and evolution expectations across Memory, JDBC, and Redis stores.
- [ ] Add automated source/binary compatibility checks and a published deprecation policy.
- [ ] Compile and run a newly generated Ktor application against the finalized handler/context API. Keep an older supported consumer fixture for compatibility verification.

### OBS-1: Observability and health

- [x] Expose scheduler lag, execution duration, failures, lease recovery/renewal failures, and dead-letter size through Micrometer/OpenTelemetry adapters or documented integration hooks.
- [x] Define bounded metric labels; execution IDs belong in logs/traces rather than unbounded metric labels.
- [x] Expose scheduler-loop and store-connectivity health with documented startup, degraded, and recovery behavior.
- [x] Preserve useful error type/diagnostic information, with guidance for sensitive payload/error data.
- [x] Extend the generated-app scenarios to verify successful and failed execution signals and health transitions during a controlled store outage. Host applications own HTTP health routes and access policy.

### OPS-1: Operator controls

- [x] Provide bounded/paginated queries by job and execution status.
- [x] Persist pause/resume state and verify that other nodes honor it without losing pending work.
- [x] Define cancellation scope explicitly, including local-versus-cross-node behavior, terminal status, and cooperative cancellation limits.
- [ ] Add DLQ inspection/replay tooling with explicit execution identity and audit behavior; treat replay as a follow-on to the initial management API.
- [ ] Define tombstoning/reconciliation for persisted jobs whose handlers were removed.
- [x] Preserve the existing `Scheduler.trigger()` capability; manual triggering is already implemented.
- [ ] Extend generated-app workflows for pause/resume, queries, supported cancellation, and DLQ replay as those capabilities land.

Use the existing [core management specification](../.specs/features/job-management-core-api/spec.md) as the starting point. Its initial scope is core APIs and local stopping; broader DLQ/reconciliation work needs separate scope. Host applications own routes, dashboards, authorization, and tenant policy.

### UPG-1: Safe upgrades

- [ ] Introduce versioned schema history and ordered migrations with repeatability/concurrent-start behavior defined.
- [ ] Upgrade populated supported previous-version databases, rather than testing only fresh schema creation.
- [ ] Preserve pending schedules, owner fencing, one-time completion markers, retries, and retained history through upgrades and restarts.
- [ ] Cover MySQL timestamp conversion, historical UTC/time-zone assumptions, and supported rolling-upgrade combinations.
- [ ] Document backups, upgrade ordering, incompatible schema changes, and rollback or explicit forward-recovery procedures.
- [ ] Add a generated-app upgrade scenario: write data with a previous release, stop it, upgrade artifacts/schema, restart with the candidate, and verify persisted behavior.

JDBC migration fixtures must cover the supported database matrix, including engines outside the current PostgreSQL generator scenario. Use separate fixtures where a generated Ktor application adds no additional coverage.

### DIST-1: Distributed failure evidence

- [ ] Define and test the lease clock-skew strategy across nodes; document the supported skew assumptions or authoritative store-time approach.
- [ ] Define process-crash recovery accounting and the policy for repeated crashes/reclaims. Catching a handler Throwable does not account for an OS-killed JVM.
- [ ] Verify stale-owner rejection and safe follow-up scheduling across worker death, delayed replies, store/network partitions, and failover.
- [ ] Verify blocking-handler isolation or document supported execution/dispatcher constraints. Cancellation requests cannot forcibly terminate arbitrary blocking side effects.
- [ ] Add controlled multi-node container scenarios with explicit fault/recovery signals instead of relying on sleeps. Reuse the generator harness for consumer-level restart checks.
- [ ] Record sustained-load/soak and bounded-resource behavior, using the existing performance suites as a baseline.
- [ ] Preserve the at-least-once contract and document handler idempotency requirements.

Full Redis Cluster support requires a cluster-aware routing/client and failover test matrix if offered. Hash tags alone establish same-slot placement, not support for every topology. Keep standalone/single-slot-proxy support boundaries explicit.

### REL-1: Release and support discipline

- [ ] Gate publishing on successful verification of the exact release commit, including the generated Ktor consumer suite.
- [ ] Validate tag/version consistency across all modules, README examples, and changelog before publishing.
- [ ] Smoke-test resolved candidate/released artifacts in a clean consumer project; `mavenLocal()` E2E alone does not verify Maven Central publication.
- [ ] Add dependency/vulnerability scanning and define dependency-update ownership; document artifact signing/provenance and SBOM expectations.
- [ ] Publish `SECURITY.md` and a vulnerability reporting process.
- [ ] Publish a supported JDK/Ktor/database/Redis deployment matrix and support/deprecation policy.
- [ ] Publish an operations runbook covering sizing, lag, unavailable stores, recovery, DLQ handling, shutdown, upgrades, and data retention.
- [ ] Reconcile the proposed reliability release numbering with the roadmap's existing Android SQLite v0.7 allocation before tagging a release.

## Validation and sign-off

For implementation changes, reproduce failures with regression tests before changing production behavior. Use unit/virtual-time and shared store contracts for deterministic semantics, native database/container fixtures for persistence and failure behavior, and the generated-app E2E suite for consumer integration. Extend the appropriate layer for each acceptance item.

Record the tested commit, commands, supported versions/backends, failure scenarios, and limitations when marking an item complete. A passing E2E baseline is evidence for its documented scenarios; the broader checklist needs its own evidence.

Release verification includes:

```bash
./gradlew clean test jacocoTestReport jacocoRootReport \
  jacocoTestCoverageVerification jacocoRootCoverageVerification
python3 .github/scripts/check_coverage.py
./gradlew :khrona-ktor:e2eTest
./gradlew :khrona-core:perfTest :khrona-store-jdbc:perfTest :khrona-store-redis:perfTest
./gradlew :khrona-core:pitest :khrona-ktor:pitest \
  :khrona-store-memory:pitest :khrona-store-jdbc:pitest
python3 .github/scripts/check_mutation_coverage.py
```

Spring Boot integration, Android SQLite, a dashboard, and full Redis Cluster support can be scheduled according to adoption needs. The supported 1.0 scope and its compatibility/operational guarantees must be explicit.
